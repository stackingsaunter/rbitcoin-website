02 / Architecture

The archive is the store.

rbitcoin keeps outputs and records their spends. To validate a new block, it looks up previous outputs in indexed history instead of maintaining a separate database of unspent coins. No UTXO set does not mean no spentness checks.

History, indexed for the next block

A conventional Bitcoin Core setup has block files alongside a UTXO chainstate. rbitcoin organizes the archive around the queries the node needs: find a transaction, resolve its outputs, check whether they are spent, reconstruct a block.

The transaction index is part of this design and is written during initial block download. It is not an optional wallet index. The store uses custom on-disk files, not a relational database server you need to install.

There is no separate coins cache to size and flush. The operating system’s page cache still matters; “no UTXO set” is not a claim that storage or RAM is free.

Three jobs in one store

A / Archive
The transaction history: headers, outputs, inputs, witness, and the data needed to reconstruct blocks.
B / Wallet indexes
Optional indexes for wallet queries, including scripthash history. Electrum and Esplora require the scripthash index.
C / Chain state
Which chain is current, transaction heights, and the spend annotations used to interpret the archive.

A historical block is reconstructed from the stored transaction parts. Wallet queries join the archive with wallet indexes and the mempool. The same process validates and serves; there is no separate Electrum indexer reading another node’s files.

This is the conceptual model, not an on-disk specification. File layouts and migration rules belong in SCHEMA.md.

Keep the hot part fast

Outputs, spends, the transaction index, and wallet indexes stay in the main data directory. Inputs and witness can live on a second, slower disk using --datadir-cold. Omit that option to keep everything together.

A hot drive sized only for 226 GiB will not cover that reported indexing peak. Plan for both working space and chain growth. These measurements come from the project’s setup guide; hardware, index selection, and chain height affect your needs.

Independent scripts. Established crypto.

The consensus and script implementation lives in this Rust codebase. It uses rust-bitcoin types and libsecp256k1 for ECDSA and Schnorr operations; it does not delegate script validation to Bitcoin Core’s interpreter.

That independence is a reason for the project to exist, and a reason to examine it carefully. Test coverage and agreement on tested cases are evidence, not proof of consensus equivalence. Read what is tested.

A result, not a speed guarantee

The official site reports initial block download in under nine hours on a laptop-class machine. It describes one measured run, not a promise for your hardware. This proposal has not reproduced that result.

Keep the milestone setting beside any sync result: the default skips some historical scripts, while --milestone 0 checks them. A useful comparison also needs the exact revision, chain height, hardware, indexes, and command. Until those conditions are comparable, a single headline is not a race between nodes.
