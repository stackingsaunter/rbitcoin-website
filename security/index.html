04 / Security

Independent consensus deserves independent scrutiny.

Mainnet sync, tip following, and wallet serving work. The project is still pre-1.0: storage formats and APIs can change, and independent validation can contain mistakes. Treat operation as high-scrutiny, not as a turnkey appliance.

Report vulnerabilities privately

security@reardencode.com

Do not post an unfixed remote, consensus-critical, or data-integrity bug in a public issue. Include the release tag or commit, build method and binary digest if available, network, impact, and a minimal reproduction.

Accepting an invalid block and rejecting a valid block both matter. So do P2P denial-of-service, misleading wallet-query results, and archive corruption. Never include seed phrases, private keys, or access tokens.

Feature requests, performance questions, and non-sensitive bugs belong in ordinary GitHub issues. The project security policy defines scope and supported releases.

What the evidence establishes

The published test program includes Bitcoin Core transaction fixtures, unmodified Core functional scripts that exercise production paths, Hornet-derived validation cases, and differential fuzzing against bitcoind.

Coverage tells you which lines a test ran. It does not establish that the assertions are sufficient, that every consensus edge case is covered, or that two implementations cannot diverge. Percentages from projects with different measurement scopes do not settle those questions.

Inspect the test methods and CI results. On mainnet, keep another implementation in view while you assess the node for your use.

Be explicit about historical scripts

The documented mainnet default is --milestone 840000. Script and signature checks at or below height 840,000 are skipped. Prevout, double-spend, maturity, and fee checks still run.

--milestone 0 enables script checking throughout history. A successful sync with the default is not evidence that every historical script was checked. Full script checking is also not a guarantee that the implementation has no consensus bugs.

Know what remains your responsibility

Monitor chain agreement, reorgs, logs, and disk space. Read migration instructions before upgrades: the pre-1.0 format is not a stable storage contract, and some changes require a fresh sync.

Protect wallet and RPC listeners with appropriate TLS and access controls. Keep secrets out of reports. The project has no long-term-support promise for this pre-1.0 period; consult the current policy rather than assuming an older release is maintained.

Version 1.0 would not make divergence impossible. The obligation to test, review, and report remains.
